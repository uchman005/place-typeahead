# Write-up

**Tradeoffs.** The browser calls my own Next.js route (`/api/places`), not Open-Meteo directly. That costs one hop but gives one normalised cache key, CDN caching (place names rarely change) and a single place for rate limits or a provider swap. A 250 ms debounce and 2-character minimum trade a little immediacy for far fewer requests; cached queries, such as when backspacing, render instantly and skip the debounce. Stale responses are handled twice: an AbortController cancels superseded requests, and a request-id guard drops any response that still arrives late. Previous results stay visible, dimmed, while the next query loads to avoid flicker, and nothing is auto-highlighted, so Enter never picks a place the user didn't choose. I hand-built the WAI-ARIA combobox rather than adding Downshift: less JavaScript shipped, more for me to own.

**Scaling and hardening.** Cache at the CDN on the normalised query with stale-while-revalidate, and add per-IP rate limiting at the edge (Redis or middleware). For production I'd replace the third-party geocoder with our own index (Postgres `pg_trgm`, or Typesense/Meilisearch) seeded with verified areas and ranked by listing volume, so "Lekki" beats a same-named village. Add upstream timeouts (already 4 s), a circuit breaker, and metrics on p95 latency and zero-result queries, which also tell product where demand is.

**Testing.** 22 Vitest and Testing Library tests cover debounce collapsing bursts into one request, out-of-order responses using controllable promises, abort of superseded requests, cache hits, empty, error and retry states, the full keyboard flow and ARIA wiring, and the route's validation, country filter, cache headers and upstream failures. Next I'd add Playwright end-to-end tests with a mocked network, axe accessibility checks, and a load test on `/api/places`.
